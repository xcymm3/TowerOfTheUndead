# 第五步：映射与界面审计验收规格

任务 ID：`direct-mapping-ui-step5`

状态：已冻结（2026-09-18）

## 范围

在不改变原版玩法、数值、逻辑标识、自动化脚本语法和既有 767 条映射关系的前提下，完成全部映射的逐项显示与语义审计，并补齐数据库外动态文案、帮助、通知、确认弹窗、结局文本以及后期窄屏可用性检查。第五步只修改主题适配、界面样式、审计工具、测试和文档；不执行第六步的存档/长离线/持续运行全量验收，也不执行第七步发布。

## 验收条件

### AC-1：767 条映射逐项审计

- 审计结果必须恰好包含 767 条唯一映射，不得遗漏、重复或出现额外条目。
- 每条映射必须记录来源组、来源键、来源 ID、亡灵主题名称、实际运行时绑定、显示检查方式、语义检查方式、检查证据、显示状态和语义状态。
- 每条映射的 `displayStatus` 与 `semanticStatus` 都必须为 `PASS`；最终报告不得包含 `UNKNOWN` 或 `FAIL`。
- 运行时绑定必须仍然指向原版实际配置对象，映射键和来源 ID 必须保持一致。

### AC-2：显示适配与原版语义隔离

- 有名称的配置必须通过运行时翻译得到指定亡灵名称；无名称配置必须通过其真实说明、奖励、要求或同类展示字段显示对应亡灵名称。
- 动态函数、getter、数组名称和后期轮换文本必须纳入检查，不得只核对静态字符串。
- 除允许修改的展示字段外，ID、花费、效果、需求、解锁条件和其他逻辑字段的值、函数或对象引用必须保持不变。
- Automator 等脚本编辑器、代码块、输入框和脚本语法不得被主题翻译污染。

### AC-3：数据库外文案查漏

- 对资源/层级、动态说明、帮助、通知、确认弹窗、结局/字幕和脚本保护分别建立明确的审计项目。
- 每个项目必须记录检查方式、实际结果和状态；最终不得以整类 `UNKNOWN` 代替检查结果。
- 帮助搜索与帮助页、代表性动态提示、至少一条通知、至少一个确认弹窗、结局/新游戏文本必须通过真实界面或运行时路径验证。

### AC-4：后期界面与窄屏可用性

- 覆盖创世、七位主宰、封印/终焉、装备槽、织机/结局等后期关键界面。
- 在 320、375、414、768、1024、1440 像素宽度逐档检查；页面不得出现不可解释的横向溢出、关键文本裁切或关键控件超出视口。
- 可见关键控件必须可命中且尺寸足以操作；正文、按钮、弹窗和状态文本不得出现明显低对比度。
- 修复发现的主题 CSS、弹窗层级、换行和窄屏布局问题，不改变原版组件逻辑。

### AC-5：文档与可复核证据

- 更新映射审计方法文档，说明逐项显示/语义检查规则、允许的展示改写范围和脚本保护边界。
- 生成机器可读的 767 条逐项审计报告、数据库外文案报告和六档界面报告；报告必须可追溯到本次新鲜测试运行。
- `evidence.md`、`evidence.json`、`verdict.json` 与 `problems.md` 必须对应本规格的每条 AC。

### AC-6：第五步相关验证

- 通过映射/文案/后期界面相关测试、源码校验、类型检查、lint、构建和正式产物冒烟。
- 第五步不得运行 Deadline-Carl，不得发布 GitHub Pages。
- 第六步约定的历史/损坏存档、全部备份类型、长离线、持续运行和原 15 项完整回归留待下一步集中执行。

## 允许改动边界

- 允许：`runtime/` 下主题显示适配与 CSS、`tests/` 与 `scripts/` 下审计/验证代码、`docs/` 下审计文档、`.agent/tasks/direct-mapping-ui-step5/` 下证据。
- 禁止：`src/` 原版游戏源码与数值、767 条映射关系、Automator 语法、存档格式、发布配置和线上部署。

## 通过定义

只有 AC-1 至 AC-6 均由同一最终源码的新鲜证据证明为 `PASS`，且不存在未解释的映射、文案或界面缺口时，才可判定第五步完成。
